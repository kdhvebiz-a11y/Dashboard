## 0. 가장 먼저 알아야 할 점

- 현재 배포 단위는 Apps Script의 `index.html`과 `대시보드.gs` 두 파일이다. 이 저장소에는 `Code.gs`가 없으며, 서버 진입점이 들어 있는 파일 이름이 `대시보드.gs`이다.
- `apps-script/v10/index.html`과 `apps-script/v10/대시보드.gs`는 빌드 산출물이고 Git에는 커밋하지 않는다. 소스는 `apps-script/v10/template.*` 및 같은 폴더의 모듈 파일이다.
- 자동 배포는 Apps Script 프로젝트의 기존 파일 전체를 읽은 다음 `index`와 `대시보드`만 교체한다. Apps Script 편집기에 별도로 존재하는 다른 파일과 공유 설정은 보존한다.
- 따라서 이 인수인계 묶음의 `deployed/` 두 파일이 현재 운영되는 대시보드 코드 전체다. Apps Script 편집기에만 있고 Git 저장소에는 없는 다른 파일은 이 저장소에서 복원하거나 열람할 수 없다.
- OAuth 토큰·클라이언트 비밀값, 후속관리 관리자 코드의 원문, 비공개 계약 원본 파일은 문서와 ZIP에 넣지 않았다. 다만 현재 배포 코드와 정확히 같게 보존하기 위해 `대시보드.gs`에는 관리자 코드의 SHA-256 검증값이, `index.html`에는 빌드 시 컴파일된 계약 스냅샷이 들어 있다. 외부 공개 저장소에는 올리지 말고 신뢰하는 계정에만 전달한다.

### 2.1 진입·데이터·캐시

| 함수 | 역할 |
|---|---|

| `collectData()` | 두 스프레드시트와 연도 탭, 후속관리 보조값을 모아 payload를 만든다. |

| `캐시비우기()` | 분할 캐시 키를 모두 지운다. |
| `collectYearDataV10(ss)` | 2025년 이후 연도 탭을 문의 원장 레코드로 변환한다. |
| `collectWeeklyMeetingDataV10()` | 실제 미팅 스프레드시트의 `YY.MM!J1:O8`을 모은다. |

운영 빌드의 실제 캐시 상수는 `CACHE_SEC=300`초, `CACHE_KEY=gsdash_v10`, `CHUNK=24000`자다. 소스 주석의 과거 6시간 설명은 낡은 설명이다. HTML 첫 화면에는 데이터를 직접 싣지 않고 `DATA=null`로 시작하며 브라우저가 비동기로 가져온다. `설치()` 트리거는 30분마다지만 캐시는 5분이므로, 트리거 사이에는 사용자의 요청이 캐시를 다시 채울 수 있다.

지원 쿼리:

- `?health=1`: `{ok:true, release:<40자 커밋>}`.
- `?data=1`: 전체 데이터 JSON.
- `?callback=name`: 검증된 콜백 이름으로 JSONP.
- `?fresh=1`: 데이터 캐시 무시.
- `?weekly=1`: 실제 미팅 주간 원본 JSON.

### 2.2 후속관리

| 함수 | 역할 |
|---|---|
| `rememberFollowupAccess(code)` / `forgetFollowupAccess(code)` | 입력한 접근 코드를 UserProperties에 기억/삭제한다. |

## 4. 확정된 업무 규칙과 숫자

### 4.1 기간 기준

- 전역 연도·월을 바꾸면 영업회의 자료의 문의 주차도 그 달로 바뀌어야 한다. 2026년 2월이면 10월 주차가 아니라 2월 주차가 나와야 한다.
- 2026년 2월 문의 주차는 현재 코드에서 `2/2~2/6`, `2/9~2/13`, `2/16~2/20`, `2/23~2/27`로 만든다.
- 문의 주차: 월요일~금요일.
- 실제 미팅 주차: 그 문의 주차의 직전 금요일~해당 목요일.
- 주간 조회는 ISO 주차를 사용하며 연도에 따라 52주 또는 53주를 모두 제공한다.
- 월 전체 문의와 주차 문의는 기준 기간이 달라 합계가 같지 않을 수 있다.
- 문의 성과는 문의 접수월 코호트로 보며, 실제 미팅 성과는 미팅 활동일로 본다. 한 문의가 1월에 접수되어 7월에 미팅됐다면 1월 문의 전환과 7월 실제 미팅 양쪽에 각각 들어간다.
- 미래 날짜의 미팅과 날짜가 없는 미팅은 실제 완료 미팅에서 제외한다.

### 4.2 분류·계산

- `B` 상태에 `소개`가 있으면 소개, 그 밖의 기재 상태는 마케팅이다.
- 마케팅과 소개 전체 문의는 원본 정의상 중복 가능성이 있으므로 단순 합산하여 전체 문의로 만들지 않는다.
- 발전사업 미팅 전환율 = 발전사업 미팅 수 ÷ 전체 사업 문의 수.
- 건당 평균 용량 = 실제 미팅 용량 합계 ÷ 실제 미팅 건수.
- 계산할 근거가 없거나 범위가 맞지 않는 값은 `0`으로 꾸미지 말고 `—`로 표시한다.
- 계약 실적은 문의·미팅 필터와 독립적인 RPS 계약 원장 기준이다.
- 계약 용량 원본 단위는 kWp이며 화면에서 필요하면 MW로 환산한다.
- 공사금액은 VAT 제외 금액이다.
- 권역 분류: 수도권(서울·경기·인천), 충청권(충남·충북·충청·대전·세종), 강원권, 영남권(부산·대구·울산·경남·경북·경상), 호남권(광주·전남·전북·전라), 제주, 기타/미분류.

### 4.3 목표

- 전체 문의: 일 50건, 주 350건, 월 1,500건.
- 발전사업 문의: 월 787건 = 마케팅 700건 + 소개 87건. 상세 원장 기반 연도에서는 이 목표를 적용할 수 없는 화면이 있어 `—`가 나올 수 있다.
- 영업회의 미팅 목표: 보고 주차당 17건. 월 목표는 `그 달 보고 주차 수 × 17건`.
- 2026년 계약 용량 연 목표: 150,000 kWp = 150 MW.
- 월별 계약 용량 목표는 RPS 빌드 데이터의 월별 목표가 있으면 그것을 우선하고, 없으면 `말` 탭의 계약 용량 목표를 사용한다.
- 브라우저에서 직접 저장한 월 목표가 있으면 해당 브라우저의 로컬 목표가 가장 우선한다.

### 4.4 표시 규칙

- 강조는 해당 숫자에만 적용하고 행·열·셀 전체에 과한 파란 배경이나 이중 테두리를 두르지 않는다.
- 차트의 선택 월은 점·라벨로 구분하고 넓은 세로 음영 띠를 사용하지 않는다.
- 영업회의 자료는 기존 HWP 형식을 최대한 유지하되, 주간 문의 → 문의 TOP 3 → 미팅가망·특이사항 → 후속 조치 순서로 보고한다.
- 화면 상단에는 컨설팅/필드/외주/입찰 업무 탭을 유지한다.
- 사이드바는 11개를 한 줄로 늘어놓지 않고 6개 그룹으로 접어 직관적으로 사용한다.

## 5. 미완료 항목과 알려진 한계

1. **가장 최근 요청 미완료:** 영업회의 자료의 `문의 주차` 변경 위치가 본문 중간이라 불편하므로 전역 연도·월 컨트롤 옆의 위쪽 영역으로 옮겨야 한다. 현재 운영 릴리스에는 아직 반영되지 않았다.
2. `필드`, `외주`, `입찰`은 상단 탭만 있고 별도 데이터 원본·파일·형식·메뉴가 연결되지 않았다.
3. 과거 영업회의 문의 주차는 연도 문의 원장의 상담번호 날짜를 사용해 재구성한다. 상담번호가 규칙을 지키지 않으면 누락될 수 있으며, `통계!AB:AO` 수기 주간 표와 반드시 같은지 실무 검증이 필요하다.
4. 영업회의 자료의 과거 미팅 상세는 주로 컨설팅 통계 원장의 실제 미팅일을 사용한다. `미팅26`의 풍부한 관계/메모 필드는 최신 연결 주차에서만 충분하므로 과거 주차의 관계 분류가 `자료 없음`으로 보일 수 있다.
5. 주간 조회 화면은 두 번째 실제 미팅 스프레드시트의 금요일~목요일 집계를 사용하지만, 영업회의 HWP 상세의 과거 미팅 목록은 첫 번째 통계 스프레드시트 원장으로 보완한다. 두 원본 사이의 차이는 계속 대조해야 한다.
6. `template.gs` 상단 주석은 캐시 6시간이라고 되어 있으나 운영 빌드는 5분이다. 기능 오류는 아니지만 문서 주석을 정리할 필요가 있다.
7. 캐시 트리거는 30분 간격인데 캐시 TTL은 5분이다. 필요하면 트리거와 TTL 정책을 다시 맞춘다.
8. Apps Script 프로젝트에 Git 저장소 밖의 편집기 전용 파일이 있다면 자동 배포는 보존하지만 이 인수인계 묶음에는 포함되지 않는다. Claude가 Apps Script API 권한 없이 그 파일 내용을 알 수는 없다.
9. 저장소가 공개 상태로 보인 적이 있으므로 계약 원본, 접근 코드, OAuth 값, 고객 상세 데이터는 절대 커밋하지 않는다.
10. `?release=...`는 캐시 방지용 쿼리일 뿐 특정 Apps Script 버전을 고정하는 기능이 아니다. 실제 운영 버전은 배포 ID가 가리키는 버전이다.

## 6. 배포와 운영

### 6.1 자동 배포

1. 로컬 저장소에서 소스 모듈을 수정한다.
2. `node scripts/build-dashboard-v10.mjs`가 `index.html`과 `대시보드.gs`를 생성한다.
3. `node --test tests/*.test.mjs`로 전체 테스트를 통과시킨다.
4. `main` 브랜치에 push하면 `.github/workflows/deploy-dashboard.yml`이 실행된다.
5. GitHub Actions는 비공개 계약 자료와 관리자 해시를 Secrets에서 주입하여 다시 빌드하고 테스트한다.
6. Apps Script API로 기존 배포 버전의 전체 파일을 읽고 `index`와 `대시보드`만 새 코드로 바꾼 임시 head를 만든다.
7. 새 Apps Script 버전을 만든 뒤 편집기 head를 원상 복구한다.
8. 기존 `DEPLOYMENT_ID`의 `versionNumber`만 새 버전으로 갱신한다. 따라서 운영 URL은 바뀌지 않는다.
9. `?health=1`의 40자 Git 커밋이 push한 커밋과 같을 때만 성공으로 처리한다. 실패하면 이전 배포 버전으로 롤백한다.

### 6.2 GitHub Actions Secrets

- `GOOGLE_CLIENT_ID`
- `GOOGLE_CLIENT_SECRET`
- `GOOGLE_REFRESH_TOKEN`
- `CONTRACT_DATA_GZIP_BASE64`
- `FOLLOWUP_ADMIN_HASH`

비밀값은 소스, 로그, 이 문서, ZIP에 복사하지 않는다.

### 6.3 배포 ID 유지 여부

유지한다. 새 웹앱을 매번 만들지 않는다. 아래 배포 ID의 버전만 교체한다.

`AKfycbzHukN_HIc7iguhO8ujKhJUO4NaPUOSkc2p3RyLe-Emq_UpH9uOOr-xGWZqHwEUkxYM`

따라서 사용자가 쓰는 기본 URL도 계속 동일하다.

### 6.4 수동 확인

- 상태: 운영 주소에 `?health=1`을 붙여 `ok:true`와 예상 커밋을 확인한다.
- 데이터 강제 새로고침: `?data=1&fresh=1`.
- 주간 미팅 원본: `?weekly=1`.
- UI: 운영 주소를 새로 열고 전역 연·월, 주간 조회, 보고자료 → 영업회의 자료를 점검한다.

## 7. 다음 작업 권장 순서

1. 영업회의 자료의 문의 주차 선택기를 전역 연·월 바로 옆 상단으로 이동한다.
2. 선택기 이동 후 2026년 2월과 10월을 오가며 문의 주차와 미팅 기간이 동시에 바뀌는지 회귀 테스트를 추가한다.
3. 실제 미팅 주간 집계와 영업회의 상세 목록의 기준 차이를 화면에 더 명확히 표시하거나 하나의 원본으로 통합한다.

5. 운영 화면 확인 후 커밋·push하여 기존 배포 ID로 자동 배포한다.
